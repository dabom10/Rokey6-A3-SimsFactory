#### ISSUE 01 — ArticulationRoot 위치와 Joint Body0 경로 불일치

##### 증상
- wheel joint에 Drive(Damping=10000, Stiffness=0) 설정했으나 바퀴가 전혀 굴러가지 않음
- `Failed to find articulation at '/Root/run_robot/body'` 경고 반복 출력

##### 원인 분석
ArticulationRoot가 `/Root/run_robot` (Xform 컨테이너)에 붙어있는 상황에서, wheel joint의 Body0이 `/Root/run_robot/body/body` (실제 RigidBody)를 가리켜 경로 불일치가 발생했음.

**잘못된 초기 이해:**
> "ArticulationRoot는 Joint Graph의 최상위 Body(링크)에 붙어야 한다 → Xform에 붙이면 안 된다"

**실제 동작:**
> Isaac Sim에서 ArticulationRoot는 Xform 컨테이너에도 붙일 수 있으며, DC API 접근 경로로 사용된다. 중요한 건 **Joint Graph 무결성** — Body0/Body1이 올바른 RigidBody prim을 가리키는지 여부.

##### 해결
- ArticulationRoot: `/Root/run_robot` 유지
- wheel joint Body0: `/Root/run_robot/body/body`로 통일
- KR210 root_joint: deactivate (Stage 계층으로 연결 유지)
- DC API 접근 시 `/Root/run_robot` 경로 사용

##### 핵심 인사이트
```
ArticulationRoot 위치 ≠ Joint Body0 경로가 반드시 일치해야 하는 것은 아님
→ DC API 핸들 획득 경로와 Joint Graph 무결성을 별개로 관리해야 함
```

#### ISSUE 02 — 역관절 및 땅파기 현상 (joint_a2 부호 오류)

##### 증상
- Pick 동작 시 어깨(`joint_a2`)가 목표물 반대 방향으로 꺾임
- 콘솔 상 수직(Z축) 오차가 크게 발생함 (실측: dZ=-2.248m)

##### 원인 분석
- `solve_ik_kr210` 내에서 `theta2` 계산 시 불필요한 음수(-) 적용
- 손끝(EE) 오프셋(`EE_OFFSET=0.3m`)이 목표 좌표에 음수로 더해져, 로봇이 큐브 윗면이 아닌 아랫쪽을 타겟으로 잡음

##### 실측 로그 (수정 전)
```
EE   : X=1.232, Y=-12.665, Z=5.422
큐브 : X=4.537, Y=-12.852, Z=3.173
diff : dX=3.305, dY=-0.187, dZ=-2.248
수평 오차(XY): 3.310m
```

##### 해결
`theta2` 부호 교정 및 `z_offset`을 양수로 적용하여 목표물 윗면 정확히 조준:

```python
# 기존 (EE 위로 솟는 현상)
theta2 = (np.pi / 2) - theta2_ik

# 수정 (부호 반전)
theta2 = -((np.pi / 2) - theta2_ik)
```

추가로 `solve_ik_kr210`에 `z_offset` 파라미터를 도입하여 shoulder 기준 Z를 보정:

```python
z_adj = z_s + z_offset  # shoulder 기준 Z 보정
# PICK 시:     z_offset = -0.3 (EE를 큐브 높이까지 내림)
# PRE-PICK 시: z_offset = +0.5 (접근 여유 높이 확보)
```

##### 미해결 상태 (세션 종료 시점)
- L_UPPER=1.25, L_FORE=1.30이 실제 KR210 링크 길이와 다를 가능성 존재
- tool0(EE)이 link_6 끝에서 추가 오프셋 존재 가능
- EE 위치 정밀 보정은 진행 중

#### ISSUE 03 — 사마귀 팔꿈치 현상 (joint_a3 축 방향 반전, Elbow-In)

##### 증상
- 수평(XY) 오차가 0.8m 이상 발생
- 팔꿈치(`joint_a3`)가 바깥으로 뻗지 않고 로봇 몸통 쪽으로 심하게 접힘

##### 원인 분석
수학적으로 팔꿈치가 위를 향하는 'Elbow Up' 자세를 계산하여 양수(+) 값을 도출했으나, **KR210 모델의 USD 조인트 축(Axis) 설계 기준이 수학적 방향과 반대**로 설정되어 있었음.

> **로봇 URDF/USD 축의 함정:** 수학적 IK 수식이 완벽하더라도, 제조사나 모델(UR10 vs KR210)에 따라 관절의 회전 방향(+/-) 기준이 다를 수 있다. 관절이 기괴하게 꺾인다면 수식의 부호를 최우선으로 점검해야 한다.

##### 해결
기구학 수식 자체를 뜯어고치는 대신, 최종 모터 값 전달 단계에서 부호 하나 추가:

```python
joint_a3 = -theta3_math  # KR210 하드웨어 축 기준에 동기화
```

#### ISSUE 05 — Stop → Play 시 wheel에 Angular Drive가 자동 생성되어 차체 이동

##### 증상
- 처음 script 실행 시엔 차체가 정지 상태
- Stop → Play 재실행 후 갑자기 wheel joint에 angular drive가 생겨 차체가 저절로 이동
- USD에서 Drive를 삭제해도 반복 발생

##### 원인
`DriveAPI.Apply(prim, "angular")`가 USD 스테이지에 Drive 속성을 **영구적으로 기록**함. Stop → Play 사이클에서도 USD 기록이 남아 있어 PhysX가 이를 읽어 차체를 움직임.

##### 해결
**wheel 조인트에 DriveAPI.Apply 자체를 하지 않음.** 대신 DC API의 `set_dof_velocity_target(dof, 0.0)`만 매 프레임 호출하는 방식으로 전환.

```python
# ❌ 잘못된 방식 — USD에 Drive가 영구 기록됨
elif name.startswith("wheel"):
    drive_api = UsdPhysics.DriveAPI.Apply(prim, "angular")
    drive_api.GetDampingAttr().Set(1e6)

# ✅ 올바른 방식 — USD에 아무것도 쓰지 않음, 런타임에만 영향
elif name.startswith("wheel"):
    self.wheel_dofs.append(dof)
    self.dc.set_dof_velocity_target(dof, 0.0)
```

> **주의:** Stage에 이미 남아있는 wheel Drive는 수동으로 삭제 필요  
> (Stage에서 wheel joint 선택 → Property → Drive 섹션 X 버튼 → USD 저장)

#### ISSUE 06 — 차체 심한 흔들림 (Physics Instability)

##### 증상
- 로봇팔 이동 시 차체가 반력으로 심하게 흔들림
- 특히 큰 각도 이동 구간에서 차체가 밀리거나 튕김
- `asyncio.sleep`으로 대기하면 흔들림이 더 심함

##### 원인 (복합)
1. **KR210 링크 inertia 경고**: `Link1`, `tool0` 등 `inertia {1,1,1}, negative mass` 경고 → 물리 연산 불안정
2. **바퀴 damping 부족**: wheel damping=1e5 → 반력을 충분히 흡수 못함
3. **asyncio.sleep 사용**: PhysX는 프레임 단위로 작동하는데, sleep은 프레임과 무관하게 시간만 기다림 → 순간 최대 토크 발생

Extension 환경에서는 이것이 더욱 심각한데, `apply_action`과 브레이크 명령이 별도로 호출될 경우 **마지막 액션이 이전 액션을 완전히 덮어씌우는(Override)** Isaac Sim Core API의 특성 때문에 브레이크 명령이 소거됨.

##### 해결 3단계

**① KR210 링크 질량/관성 직접 지정 (`_fix_kr210_mass`)**

```python
link_masses = {
    "base_link": 150.0, "Link1": 80.0, "link_2": 120.0,
    "link_3": 60.0, "link_4": 40.0, "link_5": 20.0,
    "link_6": 10.0, "tool0": 2.0
}
inertia = mass * 0.1  # 대각 관성 텐서
```

**② 바퀴 damping 강화**: 1e5 → 1e6

**③ `asyncio.sleep` → `lerp_to` + `next_update_async()`로 교체**

Script Editor 환경에서는 lerp 보간으로, Extension 환경에서는 팔 이동 목표와 바퀴 브레이크를 `np.concatenate`로 **하나의 통합 배열로 묶어 단 1회의 `ArticulationAction`으로 전송**하는 방식으로 해결.

```python
# Script Editor 방식: 프레임 보간
async def lerp_to(self, targets_dict, steps=60):
    current = {name: dc.get_dof_state(dof).pos for name, dof in ...}
    for step in range(1, steps + 1):
        t = step / steps
        for name, target in targets_dict.items():
            interp = current[name] + (target - current[name]) * t
            dc.set_dof_position_target(dof_handles[name], interp)
        self._brake_wheels()   # 매 프레임 바퀴 velocity=0 재적용
        await app.next_update_async()

# Extension 방식: 단일 트랜잭션
# 팔 관절 목표 배열 + 바퀴 브레이크 배열을 하나로 병합
combined_action = ArticulationAction(
    joint_positions=np.concatenate([arm_targets, np.zeros(4)])
)
robot.apply_action(combined_action)
```

##### 핵심 인사이트
```
asyncio.sleep은 물리 제어에 절대 사용하지 말 것
→ PhysX는 프레임 단위로 동작 → next_update_async()로 프레임 동기화 필수

Isaac Sim Core API의 단일 트랜잭션 원칙:
→ 동일 Articulation에 한 프레임 내 다중 apply_action 호출 시 마지막 것만 적용
→ 팔 + 바퀴 제어를 반드시 하나의 배열로 병합하여 단일 전송

차체 흔들림은 단일 원인이 아님:
→ 링크 질량 + 바퀴 damping + 관절 제어 방식 세 가지 모두 수정해야 안정화
```

#### ISSUE 09 — 컨베이어 큐브 감지 방식

##### 초기 방식: 좌표 임계값 기반 (문제 있음)
```python
CONVEYOR_AXIS = 'x'
CONVEYOR_THRESHOLD = -6.0
# X < -6.0 이면 "끝에 도달"로 판단
```
문제: 임계값 튜닝이 필요하고, 큐브가 이미 정지해 있어도 트리거되지 않음

##### 최종 방식: 3초 정지 감지 (채택)
```python
STABLE_SEC    = 3.0     # 정지 판단 시간 (초)
MOVE_THRESH   = 0.005   # m 단위, 이 거리 이상 움직이면 이동 중 판단
STABLE_FRAMES = 180     # 60FPS × 3초

# 매 프레임 이전 위치와 비교
moved = np.linalg.norm(cube_pos - prev_pos)
if moved > MOVE_THRESH:
    stable_count = 0   # 움직임 감지 → 리셋
else:
    stable_count += 1  # 정지 중

if stable_count >= STABLE_FRAMES:
    # pick 시작
```

> 컨베이어 진동/떨림이 있으면 `MOVE_THRESH`를 0.01~0.02로 상향 조정

#### ISSUE 10 — Standalone 방식의 씬 로드 실패 및 프리징

##### 증상
- 터미널에서 `isaacsim.sh standalone_pnp.py` 실행 시 기존 환경이 로드되지 않고 빈 화면(New Stage) 출력
- `asyncio.get_event_loop().run_forever()`가 렌더링 스레드를 블로킹하여 화면이 멈춤

##### 원인
Standalone 스크립트는 시뮬레이터 외부에서 강제로 엔진을 부팅하고 제어하므로 경로 인식이 까다롭고, 비동기 루프 관리가 엄격하지 않으면 UI가 멈추는 치명적 단점이 존재함. 특히 지속적인 통신이 필요한 ROS 2 노드(`rclpy.spin`)와 결합 시 교착 상태(Deadlock) 확률이 매우 높음.

##### 해결 — 아키텍처 대공사

Standalone 방식을 폐기하고 NVIDIA 공식 권장 방식인 **Extension (`BaseSample` 상속)** 구조로 전면 재구축:

```
ext_kr210/
├── extension.toml       ← 패키지 메타데이터
├── __init__.py
├── extension.py         ← 시뮬레이터 이벤트 훅
└── kr210_sample.py      ← BaseSample 상속, 실제 로직
```

`physics_step` 안에서 매 물리 프레임마다 제어 로직을 실행함으로써 시뮬레이터 내부의 이벤트 루프와 물리 엔진 스텝에 코드를 안전하게 기생시키는 형태로 변경.

#### ISSUE 11 — Extension 패키지 검색 실패

##### 증상
Extensions 창 Search Paths에 경로를 추가했음에도 검색 결과가 비어 있음.

##### 원인 (3가지 복합)
1. **리눅스 경로 표기 오류:** 경로 중간에 틸드(`~`)와 절대 경로(`/home/rokey/...`)가 혼용 → 내부 파일 탐색기가 이를 해석 불가
2. **폴더 스캔 규칙:** Isaac Sim은 등록된 경로 "내부의 하위 폴더"를 뒤져 `extension.toml`을 찾음 → 패키지 폴더(`ext_kr210`) 자체가 아닌 그 **부모 폴더**를 등록해야 함
3. **탭 필터링:** 유저가 생성한 커스텀 패키지는 공식 `NVIDIA` 탭이 아닌 **`THIRD PARTY`** 탭에 격리되어 표시되는데, 이를 인지하지 못함

##### 해결
경로 오타 수정 + 부모 디렉토리로 재등록 + 필터 제거 후 `THIRD PARTY` 탭에서 활성화

#### ISSUE 12 — 바닥 증발 에러 (Reference vs Sublayer)

##### 증상
- `add_reference_to_stage` 사용 시 로봇만 로드되고 `/BlackGrid` 바닥 통째로 소멸
- `Prim path expression is invalid` 에러로 물리 스텝 진행 불가

##### 원인
`add_reference_to_stage` 함수는 USD 파일 내에 지정된 **'Default Prim(기본 폴더)' 하나만을 타겟으로 가져옴**. 원본 `basic.usd`는 로봇(`/Root`)과 바닥(`/BlackGrid`)이 별도의 최상위 폴더로 분리된 **다중 루트 구조**였기에 바닥이 누락됨.

##### 해결 — Sublayer 방식 도입

```python
# ❌ Reference 방식 — Default Prim만 가져옴
add_reference_to_stage(usd_path, prim_path)

# ✅ Sublayer 방식 — 모든 계층을 100% 원본 그대로 겹쳐 로드
stage.GetRootLayer().subLayerPaths.append(usd_path)
```

투명한 셀로판지를 겹치듯 USD 파일의 모든 계층(Layer)을 현재 스테이지에 병합. 바닥, 조명 등 다중 루트 구조 완벽 보존.

> **USD Composition 핵심 원칙:**  
> 개별 객체를 독립적으로 추가할 때는 `Reference`,  
> 전체 환경 맵 세팅(다중 루트)을 덮어씌울 때는 `Sublayer` 사용.

#### ISSUE 13 — 오브젝트 바닥 관통 및 추락

##### 증상
스폰된 책(큐브)이 컨베이어 벨트를 뚫고 바닥으로 추락.

##### 원인
3D 그래픽/물리 엔진에서 물체의 `Position`은 물체의 '정중앙(Center of Mass)'. 컨베이어 표면 높이(Z=1.96)에 책을 스폰하면 아래쪽 절반이 컨베이어 메쉬 내부로 파고들게 되어(Penetration) 물리 엔진이 튕겨 내거나 추락시킴.

##### 해결
Z축 스폰 좌표를 `1.96` → `2.8`로 상향하여 허공에서 스폰 후 자유낙하, 컨베이어 표면에 자연스럽게 안착.

#### ISSUE 14 — 카메라 뷰포트 강제 고정

##### 증상
Python 스크립트로 추출한 명당 카메라 좌표를 코드에 삽입했으나, 실행 시 기본 시점(`[1.5, 1.5, 1.5]`)으로 리셋됨.

##### 원인
코드가 주입된 `setup_scene` 함수는 시뮬레이터가 USD 에셋을 메모리에 로드하기 위해 준비하는 극초기 단계. 이 단계에서 뷰포트를 설정하더라도, 로딩이 완료되고 엔진이 "Play" 상태로 전환될 때 내부적으로 카메라 뷰를 기본값으로 덮어쓰는 라이프사이클(Lifecycle)이 존재함.

##### 해결
뷰포트 설정 코드(`set_camera_view`)의 위치를 물리 엔진이 구동되기 시작하는 `setup_post_load` 함수 내부, **`await self._world.play_async()` 바로 직후**로 이동.

```python
async def setup_post_load(self):
    await self._world.play_async()
    # ← 바로 이 위치에서 카메라 설정 (엔진 초기화 완료 직후)
    set_camera_view(eye=[...], target=[...])
```


## 8. 핵심 인사이트 종합

### Isaac Sim 물리/API 설계

1. **ArticulationRoot는 Xform에도 붙일 수 있음**  
   DC API 접근 경로와 Joint Body0/1 경로가 일치하지 않아도 작동 가능. 중요한 건 Joint Graph 무결성. DC API 핸들 획득 경로와 Joint Graph 무결성을 별개로 관리할 것.

2. **DriveAPI.Apply()는 USD에 영구 기록됨**  
   Stop→Play 사이클에서도 설정이 유지되므로, 런타임에만 적용하려면 Apply 없이 velocity_target만 사용할 것. 이미 기록된 Drive는 Stage에서 수동 삭제 필요.

3. **asyncio.sleep은 물리 제어에 절대 금지**  
   PhysX는 프레임 단위 동작. `next_update_async()` + lerp 보간 조합이 유일하게 안전한 접근법.

4. **Isaac Sim Core API의 단일 트랜잭션 원칙**  
   동일 Articulation에 한 프레임 내 다중 `apply_action` 호출 시 마지막 것만 적용. 팔 + 바퀴 모든 관절 제어를 하나의 배열로 묶어 단일 전송해야 함. 향후 ROS 2 `Twist` 메시지와 로봇팔 제어 명령이 동시에 들어올 때도 반드시 준수.

5. **차체 흔들림은 단일 원인이 아님**  
   링크 질량 오류 + 바퀴 damping 부족 + 순간 토크 세 가지가 복합 작용. 하나만 고쳐서는 안정화 불가.

6. **Isaac Sim 5.0에서 USD 24 API 시그니처 변경**  
   기존 코드 그대로 사용 시 ArgumentError 발생. 버전 이전 시 API 시그니처 전수 검사 필요.

### 로봇 기구학

7. **로봇 USD 조인트 축 방향은 반드시 실측 확인**  
   수학적 IK 수식이 완벽하더라도 제조사/모델별로 관절 회전 방향(+/-) 기준이 다름. 관절이 기괴하게 꺾이면 수식의 부호를 최우선 점검. UR10과 KR210은 같은 6축 로봇이어도 축 방향이 다를 수 있음.

8. **IK 목표점 ≠ 실제 접촉점**  
   큐브 중심이 아닌 윗면, 그리퍼 오프셋 등을 z_offset으로 보정. `print_ee_error()`로 오차를 실측하는 루틴이 반드시 필요. 이미지만으로는 정량적 오차 파악 불가.

### USD 씬 구성

9. **USD Composition: Reference vs Sublayer**  
   개별 객체 추가는 `Reference`, 전체 환경 맵(다중 루트 구조)은 `Sublayer`. 바닥/조명/로봇이 각각 최상위 폴더로 나뉘어 있다면 Sublayer만이 원본 구조를 100% 보존함.

10. **오브젝트 스폰 좌표는 Center of Mass 기준**  
    표면 높이에 스폰하면 물체 절반이 메쉬 내부로 파고듦(Penetration). 자유낙하 여유를 주어 스폰할 것.

### 아키텍처 및 ROS 2 연동

11. **Extension 아키텍처는 ROS 2 연동의 전제조건**  
    GUI Script Editor나 Standalone 방식은 `rclpy.spin`과 결합 시 반드시 스레드 충돌이나 UI 프리징을 유발. `BaseSample` 상속 기반 Extension에 `physics_step`을 두고 그 안에서 ROS 2 콜백 데이터를 로봇에 씌우는 구조가 유일하게 안전한 표준 접근법.

12. **카메라 뷰포트 설정 타이밍**  
    `setup_scene`이 아닌 `play_async()` 이후의 `setup_post_load`에서 설정해야 엔진 초기화로 인한 리셋을 방지. 시뮬레이터 라이프사이클을 이해하고 코드 삽입 위치를 결정할 것.

13. **디버깅은 캡처 이미지 + 콘솔 로그 병행이 효과적**  
    단계별 PNG 캡처로 자세 확인, 콘솔 좌표 로그로 정량적 오차 분석. 이미지만으로는 수치 파악 불가, 로그만으로는 공간적 맥락 파악 불가. 두 가지를 반드시 병행할 것.

## 9. 향후 ROS 2 연동 로드맵

현재 완성된 Extension 프레임워크는 단순히 책을 줍는 애니메이션이 아니라, **"언제든 ROS 2 통신 모듈을 끼워 넣을 수 있는 완벽한 시뮬레이션 기반(Base)"**으로서의 가치를 가짐. 향후 `rclpy.create_node()`를 `setup_post_load`에 안전하게 배치하고, `physics_step` 안에서 `cmd_vel` 콜백 데이터를 로봇 바퀴에 씌우는 최적의 구조가 이미 갖춰진 상태.

```
Extension physics_step 안에서:

[ROS 2 구독] cmd_vel (Twist)        → 바퀴 velocity_target 계산
[ROS 2 구독] arm_target (JointState) → KR210 position target 계산
[배열 병합]  np.concatenate([arm_targets, wheel_targets])
[단일 전송]  robot.apply_action(ArticulationAction(joint_positions=combined))

[ROS 2 발행] 라이다 센서 데이터 → LaserScan 토픽
[ROS 2 발행] 카메라 이미지     → Image 토픽
[ROS 2 발행] 로봇 상태         → JointState, Odometry 토픽
```

**핵심 포인트:** 모든 구독 콜백은 `physics_step` 내부에서 처리하거나, 스레드 안전한 큐(Queue)를 통해 데이터를 넘겨야 렌더링 루프와의 충돌을 방지할 수 있음. 팔과 바퀴 제어는 항상 단일 트랜잭션으로 처리.
