### 1-1. 시스템 목적

핵심 기술 요소는 다음과 같다.

- Articulation 기반 UR10 매니퓰레이터 제어
- USD Stage 구조 기반 씬 관리
- Standalone Python에서의 PhysX 생명주기 안정화
- 디지털 트윈 구조 확장 가능성 확보

### 1-2. 전체 동작 플로우

```
컨베이어 벨트
    → 책(큐브) 진입 및 색상 인식 (RGB Camera + OpenCV HSV)

    → AMR 차체 상단 박스 위치로 이동 및 Detach
    → AMR Nav2 자율 주행 → 목적 서가 구역 도달
    → 재적재 Pick & Place 수행
    → IDLE 복귀
```

### 1-4. 개발 전략

### Issue #1 — Isaac Sim 5.0.0 API 마이그레이션: ArticulationController Import 실패

**초기 가정**

Isaac Sim 4.x 버전대의 `omni.isaac.core` 패키지 구조가 5.0.0에서도 동일하게 유지될 것이라 가정했다.

**오류 내용**

```
ImportError: cannot import name 'ArticulationController'
             from 'omni.isaac.core.controllers'
```

**오류 원인 분석**

Isaac Sim 5.0.0에서 Core API가 별도 익스텐션(`isaacsim.core.api`)으로 분리·재구성됐다. 릴리즈 노트를 확인하니 `APP_SCRIPT.sh --enable isaacsim.core.api` 인자가 필요하고 Python 모듈 경로 전체가 변경되어 있었다.

**해결**

Import 경로 전면 수정:

```python
# 변경 전
from omni.isaac.core.controllers import ArticulationController

# 변경 후
from isaacsim.core.api.controllers import ArticulationController
from isaacsim.core.api.objects import VisualMaterial
```

이후 `SimulationContext` 객체 초기화 시 컨트롤러가 정상 바인딩됨을 확인했다.

**인사이트**

메이저 버전 업그레이드 시 API 경로는 반드시 릴리즈 노트와 공식 레퍼런스(`isaacsim.core.api` 문서)를 선행 확인해야 한다. 특히 Isaac Sim처럼 Extension 기반으로 모듈이 분리되는 구조에서는 단순 패키지명 변경이 아니라 아키텍처 자체가 재편될 수 있다.

### Issue #2 — ArticulationRoot 위치 혼동: `/ur10` vs `/run_robot`

**초기 가정**

UR10을 직접 제어하려면 `/ur10`이 Articulation Root일 것이라고 가정하고, `/ur10` 경로로 `SingleManipulator`를 생성했다.

**실제 Stage 구조**

```
/Root/robot/run_robot      ← ArticulationRootAPI 적용 위치
    └── ur10               ← 단순 하위 Prim, ArticulationRootAPI 없음
```

Stage 진단 로그:

```
📌 TARGET 경로 검사: /Root/robot/nova_carter/ur10
  ✔ Prim 존재함
  - ArticulationRootAPI : False
  - RigidBodyAPI        : True
```

**오류 원인**

USD에서 Articulation은 "경로 기반"이 아니라 **"물리 트리 기반"**으로 동작한다. Articulation Root가 `/run_robot`이면 그 아래 모든 조인트는 하나의 Articulation으로 묶인다. `/ur10`은 단지 그 트리의 하위 링크일 뿐이고, Controller는 Articulation Root 기준으로 작동하므로 `/ur10`으로 인스턴스를 만들면 ArticulationRootAPI schema가 적용되지 않아 silent failure가 발생한다.

**디버깅 방법**

Stage Traverse 코드로 ArticulationRootAPI가 적용된 Prim을 직접 탐색했다:

```python
from pxr import UsdPhysics
import omni.usd

stage = omni.usd.get_context().get_stage()
for prim in stage.Traverse():
    if prim.HasAPI(UsdPhysics.ArticulationRootAPI):
        print(f"ArticulationRoot: {prim.GetPath()}")
# 출력: ArticulationRoot: /Root/robot/run_robot
```

**해결**

`prim_path`를 `/Root/robot/run_robot`으로 수정하고 `Robot` 인스턴스 생성:

```python
from isaacsim.core.api.robots import Robot
ur10 = Robot(prim_path="/Root/robot/run_robot", name="ur10")
```

**인사이트**

USD Stage 경로는 절대 추측하지 않는다. USD 파일을 추가하거나 환경이 변경될 때마다 Stage Traverse로 실제 Articulation Root 경로를 먼저 확인하는 것이 디버깅 시간을 크게 줄여준다. Isaac Sim은 경로 하나만 틀려도 에러 메시지 없이 silent failure로 Controller가 무반응 상태가 된다.

### Issue #3 — Articulation 초기화 타이밍: `initialize()` 호출 순서 오류

**초기 가정**

`World` 객체 생성 직후 `Robot` 인스턴스를 만들고 바로 `apply_action()`을 호출하면 될 것이라 생각했다.

**오류 내용**

```
[Error] ArticulationController is not initialized. Call initialize() first.
RuntimeError: Physics handle is not valid. Call world.reset() before using articulation.
```

**오류 원인 분석**

`world.reset()`은 단순히 씬을 초기화하는 것이 아니라 PhysX 시뮬레이션 뷰(`SimulationView`)를 생성하고 Stage의 Physics Scene과 연결하는 작업이다. 이 작업이 완료되기 전에 `robot.initialize()`를 호출하면 `physics_sim_view`가 None 상태이므로 내부 `ArticulationController` 바인딩이 실패한다.

**해결**

`world.reset()` 이후 `simulation_app.update()`를 최소 1~2회 실행하여 PhysX가 완전히 준비된 이후에 `initialize()`를 호출한다:

```python
world = World()
world.scene.add(Robot(prim_path="/Root/robot/run_robot", name="ur10"))
world.reset()

for _ in range(2):
    simulation_app.update()  # Physics 준비 대기

ur10 = world.scene.get_object("ur10")
ur10.initialize()
```

**인사이트**

Isaac Sim Standalone에서 Articulation 제어 순서는 반드시 다음을 따라야 한다: **(1) World/Scene 설정 → (2) `world.reset()` 호출 → (3) `simulation_app.update()` 1회 이상 → (4) `robot.initialize()` → (5) `apply_action()` 사용.** 이 순서를 지키지 않으면 Physics Handle이 유효하지 않아 대부분의 Articulation API가 예외를 던진다.

### Issue #4 — Damping/Stiffness 파라미터로 인한 관절 응답 저하

**증상**

관절이 의도보다 느리게 수렴하고 목표 위치 도달이 지연되며 제어가 불안정했다.

**Stage 진단 결과:**

```
[PhysicsRevoluteJoint]
Stiffness : 0.0
Damping   : 100,000.0
```

**원인 분석**

Stiffness가 0이면 사실상 Position Control이 불가하고 Velocity Damping 위주로만 동작한다. 과도한 Damping은 관절 응답을 심하게 저하시킨다. 특히 `MOVE_TO_PREGRASP` → `LOWER` 전이 시 Target Position이 한 프레임 만에 0.1m 이상 급변하면 `stiffness: 1000.0`으로 설정된 UR10 조인트에서 순간적으로 과도한 제어 토크가 발생하면서 궤적 떨림(Jittering)이 생긴다.

**해결**

두 가지를 병행했다.

첫째, Task Orchestration 단에서 단순 Joint Interpolator(선형 보간)를 적용해 Target Position을 스무딩 처리했다.

둘째, 상태 전이 간 0.5초의 Wait State를 부여해 운동 에너지가 감쇠될 시간을 확보했다:

```python
# 수렴 확인 로직
current_joints = ur10.get_joint_positions()
error = np.max(np.abs(current_joints - target_joints))
if error < 0.01:  # 0.01 rad 임계값
    state = State.ATTACH
```

**인사이트**

`apply_action()`은 비동기적 요청에 가깝다. 실제 수렴은 PhysX Solver의 PD 제어와 Stiffness/Damping 파라미터에 의존하므로, State Machine의 각 Motion 상태는 반드시 수렴 확인 조건을 포함해야 한다. 특히 `LOWER → ATTACH` 전이가 가장 민감하다.

### Issue #5 — Object Localization 좌표계 불일치: World Frame vs UR10 Base Frame

**증상**

카메라가 인식한 책(Cube)의 위치로 UR10 End-Effector를 이동시켰으나, 목표점과 실제 도달 위치가 약 0.8m 어긋났다.

**초기 가정**

`cube_prim.GetWorldPose()`에서 반환된 World 좌표계를 IK 모듈에 그대로 입력해도 무방하다고 생각했다.

**원인 분석**

로봇이 원점(0, 0, 0)이 아닌 특정 위치에 Spawn되어 있었고, IK Solver는 로봇의 Base Frame을 기준(Origin)으로 구동된다. 입력 좌표는 World Frame이므로 불일치가 발생했다.

**해결**

객체 Pose를 UR10 Base Frame 기준으로 변환하는 Homogeneous Transformation 연산을 추가했다:

```python
import numpy as np

# World Pose 획득
cube_pos, _  = cube_prim.get_world_pose()
base_pos, _  = base_prim.get_world_pose()

# Base Frame 기준 변환 (회전이 없는 경우 단순화)
local_target_pos = cube_pos - base_pos

# Pre-grasp Z축 Offset 적용
pre_grasp_pose = local_target_pos + np.array([0.0, 0.0, 0.1])
```

**인사이트**

좌표계 불일치는 로봇 시스템에서 가장 흔하고 가장 소리 없이 오류를 만드는 원인이다. Perception 레이어(카메라)는 카메라 프레임, Manipulation 레이어(UR10)는 Base Frame, Navigation은 World Frame을 쓴다. 이 세 프레임 간 변환 관계를 명확히 정의하고 코드에서 일관되게 다루지 않으면, 인식은 성공해도 동작은 항상 엉뚱한 곳으로 향한다. 가장 안전한 방법은 `get_world_pose()`로 World Frame 좌표를 얻고 Base Frame으로 변환하는 명시적 파이프라인을 항상 거치는 것이다.

### Issue #6 — Fake Grasp 시 Parenting 후 큐브 순간이동(Teleport) 현상

**증상**

`ATTACH` 상태에서 `cube.SetParent(gripper)`를 호출하는 순간 책(Cube)이 Gripper 원점으로 순간이동하며 PhysX Explosion이 발생했다.

**초기 가정**

`SetParent`로 부모를 변경하면 객체의 현재 World Transform이 자동으로 유지될 것이라 생각했다.

**원인 분석**

USD에서 Prim의 Transform은 부모 좌표계(Local Space) 기준으로 저장된다. 부모가 바뀌면 기존 Local Transform 데이터(Translate, Rotate, Scale)는 유지되지만 이 값이 **새로운 부모 좌표계에서 재해석**되므로 World 위치가 달라진다.

예를 들어 큐브의 Local Position이 `(1, 0, 0)`이었을 때, World 원점 아래에서는 World Position `(1, 0, 0)`이지만 Gripper 아래로 부모가 바뀌면 Gripper 좌표계 기준 `(1, 0, 0)`이 되어 World Position이 완전히 달라진다.

**해결**

부모 변경 전 World Pose를 캐싱하고, 변경 직후 즉시 재적용하는 3단계 패턴을 적용했다:

```python
# 1. World Pose 저장
world_pos, world_ori = cube_prim.get_world_pose()

# 2. Parent 변경
import omni.kit.commands
omni.kit.commands.execute('ParentTo',
    target_path='/Root/robot/run_robot/ur10_tool0/cube',
    parent_path='/Root/robot/run_robot/ur10_tool0',
    keep_transform=True   # ← 이 옵션이 가장 안정적
)

# 3. World Pose 재적용 (keep_transform이 없는 경우 수동 처리)
cube_isaac.set_world_pose(position=world_pos, orientation=world_ori)
```

Place 단계의 Detach(World로 Parent 복귀)도 동일한 패턴이 적용된다.

**인사이트**

USD Parenting은 항상 **"World Pose 저장 → Parent 변경 → World Pose 재적용"** 3단계를 세트로 수행해야 한다. 이 규칙을 어기면 Fake Grasp의 핵심인 "물체가 Gripper에 붙어 있다"는 시각적·논리적 일관성이 무너지고 PhysX Explosion으로 시뮬레이션이 붕괴된다.

### Issue #7 — OpenCV 색상 인식 파이프라인: RGB uint8 정규화 누락

**증상 및 커밋 배경**

`[pnp] OpenCV 색상 탐지` 커밋에서 명시된 것처럼, 초기 파이프라인에서 Isaac Sim 카메라 이미지가 float32 (0~1 범위)로 반환되는 것을 uint8 (0~255)로 변환하지 않고 OpenCV에 직접 넘겼다. 결과적으로 HSV 변환 결과가 전부 0이 되면서 색상 인식이 완전히 실패했다.

**해결**

정확한 전처리 파이프라인을 구성했다:

```python
import cv2
import numpy as np

# Isaac Sim 카메라 이미지는 float32 (0~1)
img_float = camera.get_rgba()[:, :, :3]          # Alpha 채널 제거

# 1. float32 → uint8 정규화
img_uint8  = (img_float * 255).astype(np.uint8)

# 2. RGB → BGR (OpenCV 포맷 변환)
img_bgr    = cv2.cvtColor(img_uint8, cv2.COLOR_RGB2BGR)

# 3. BGR → HSV
img_hsv    = cv2.cvtColor(img_bgr, cv2.COLOR_BGR2HSV)

# 4. Red 이중 Mask (Hue 0도 경계 처리)
mask_red1  = cv2.inRange(img_hsv, np.array([0,   100, 80]), np.array([10,  255, 255]))
mask_red2  = cv2.inRange(img_hsv, np.array([170, 100, 80]), np.array([180, 255, 255]))
mask_red   = cv2.bitwise_or(mask_red1, mask_red2)

# 5. Morphology 처리 (노이즈 제거)
kernel     = np.ones((5, 5), np.uint8)
mask_red   = cv2.morphologyEx(mask_red, cv2.MORPH_OPEN, kernel)
```

**인사이트**

Isaac Sim의 카메라 출력은 float32 형식이다. OpenCV의 HSV 변환은 uint8(0~255)를 전제하므로 변환 전 반드시 정규화가 필요하다. 또한 Red는 HSV Hue 값이 0도 경계에 걸치므로 단일 범위로는 절반을 놓친다. 이중 Mask OR 처리는 Red 계열 색상을 다룰 때 필수다.

### Issue #9 — 컨베이어 벨트 끝 큐브 포즈 변형 문제

**커밋에서 발견된 이슈**

### Issue #10 — 세션 상태 오염: 코드 변경 후에도 동일 동작 반복

**증상**

코드를 수정했는데도 이전과 동일한 동작이 반복됐다. Joint 값을 바꿔도 반영이 안 됐다.

**분석 로그:**

```
[Warning] using high frequency span is disabled
[Warning] attribute viewPickingId not found
```

**원인**

Isaac Sim은 세션 상태가 남아있으면 이전 World Instance나 Stage 캐시가 그대로 유지된다. `SimulationApp`을 완전히 종료하지 않고 재실행하거나, `world.reset()`을 제대로 관리하지 않으면 변경 사항이 무시된다.

**해결**

- `SimulationApp` 완전 종료 후 재실행
- Stage clear 후 재로드
- `world.reset()` 구조를 초기화 순서에 명시적으로 배치

**인사이트**

Isaac Sim은 세션 상태 영향이 크다. 반드시 clean 상태에서 검증해야 하고, 디버깅 중 "코드가 맞는데 동작이 이상하다"는 느낌이 들면 가장 먼저 세션 완전 종료 후 재시작을 시도한다.

## 5. 시스템 아키텍처 변경 사항

### 5-1. API 마이그레이션 (omni.isaac.core → isaacsim.core.api)

Isaac Sim 5.0.0 업데이트에 따라 구형 `omni.isaac.core` API를 `isaacsim.core.api`로 전면 마이그레이션했다.

| 구분 | 변경 내용 |
|------|-----------|
| AMR (주행부) | ROS2 Action Graph 기반 Differential Controller. Nav2 `/cmd_vel` 구독, Odom/TF Publish |
| UR10 (조작부) | ROS2 Action Graph 미사용. Python Standalone에서 `ArticulationController` 직접 호출 |
| Camera | ROS2 브리지 불필요. Python에서 직접 이미지 획득 후 OpenCV 처리 |

### 5-2. State Machine (TaskManager) 도입

단일 스크립트 절차적 코드에서 발생하던 상태 꼬임 문제를 해결하기 위해 명시적 State Machine을 설계했다.

```
IDLE
  → MOVE_TO_PREGRASP  (수렴 조건: joint error < 0.01 rad)
  → LOWER             (수렴 조건: joint error < 0.01 rad)
  → ATTACH            (Parenting 수행: World Pose 저장 → SetParent → 재적용)
  → LIFT              (수렴 조건: joint error < 0.01 rad)
  → MOVE_TO_PLACE     (수렴 조건: joint error < 0.01 rad)
  → DETACH            (Parenting 해제: World Pose 저장 → SetParent(World) → 재적용)
  → RETREAT           (수렴 조건: joint error < 0.01 rad)
  → IDLE
```

각 Motion 상태는 반드시 수렴 확인 조건을 통과한 뒤에야 다음 상태로 전이한다.

### 5-3. 전체 Standalone 실행 구조

```python
simulation_app = SimulationApp({"headless": False})

world = World()
world.scene.add(Robot(prim_path="/Root/robot/run_robot", name="ur10"))
world.reset()

for _ in range(2):
    simulation_app.update()  # Physics 준비 대기

ur10 = world.scene.get_object("ur10")
ur10.initialize()

while simulation_app.is_running():
    world.step(render=True)
    task_manager.step()     # State Machine 한 스텝 실행
```

## 6. 검증 결과

**Perception–Manipulation 통합 테스트**

OpenCV HSV 기반 색상 인식으로 Red/Blue/Yellow 큐브 위치를 98% 이상 신뢰도로 추출했다 (고정 카메라, 일정 조명 조건). 추출된 좌표 기반 `pre_grasp_pose → grasp_pose` 하강 동작 오차율 10mm 이내 도달을 확인했다.

**State Machine 검증**

`IDLE → RETREAT`까지 8단계 State Machine이 로직 꼬임 없이 10회 연속 동작했다. Fake Grasp(`ATTACH`, `DETACH`) 단계에서 PhysX Explosion이 완전히 억제됐다.

**AMR 주행 연동 테스트**

Nav2 `/cmd_vel`이 Isaac Sim 내 Differential Controller 조인트(Velocity Control, `stiffness: 0.0`, `damping: 100,000.0`)에 정상 매핑되어 차체가 부드럽게 주행함을 확인했다.

## 7. 아키텍처 관점 정리

### 7-1. 기능 중심에서 구조 중심으로의 전환

오전 내내 Articulation 초기화 오류와 씨름하면서 깨달은 것은, Isaac Sim API를 "함수 사용법"으로만 접근했다는 점이다. `apply_action()`이 뭘 받는지, `robot.initialize()`가 언제 필요한지 같은 피상적인 지식으로 코드를 짜다 보니 실행 순서와 상태 의존성을 놓쳤다.

Isaac Sim의 `World / Scene / SimulationContext` 계층은 단순한 래퍼가 아니라 PhysX 시뮬레이션 생명주기를 추상화한 것이다. 이를 "구조"로 이해하고 나니 이후 발생하는 대부분의 초기화 오류가 같은 원인에서 비롯됨을 빠르게 파악할 수 있었다.

### 7-2. USD Stage 이해의 중요성

Isaac Sim은 그래픽 툴이 아니라 **USD 기반 구조 시스템**이다. 핵심 이해 사항:

- USD의 모든 것은 Prim이고, Prim들은 계층 트리를 이룬다.
- Prim에 API Schema(ArticulationRootAPI, PhysicsRigidBodyAPI 등)를 적용하면 특정 물리 시뮬레이션 객체로 동작한다.
- 레퍼런스로 로드된 USD 파일은 내부 Prim 계층을 그대로 유지한 채 참조 지점 아래에 붙는다.
- **경로 기반 추측은 반드시 실패한다.** Stage Traverse가 유일한 신뢰할 수 있는 확인 수단이다.

### 7-3. 디지털 트윈 관점에서의 재해석

Fake Grasp의 Parenting 방식은 물리 엔진 기반의 진짜 파지와 다르지만, "그리퍼가 물체를 잡고 있는 상태"라는 물리적 관계를 논리적으로 표현한 것이다. 실로봇에서는 힘 센서나 진공 흡착 피드백으로 파지 여부를 판단하겠지만, 시뮬레이션에서는 USD의 Parent-Child 계층으로 이 관계를 표현한다.

이 매핑이 얼마나 정확한지가 Sim-to-Real Gap에 직접 영향을 준다. 단순히 "시각적으로 그럴듯하게 보이는" 수준을 넘어 "실제 시스템이라면 이 상태에서 어떤 값을 가질까"를 항상 염두에 두고 설계해야 한다.

### 7-4. 팀 병렬 개발에서 발생하는 통합 이슈

오늘 커밋 로그를 보면 세 명이 동시에 로봇 제작, 환경 구성, 액션 그래프 설정을 병렬로 진행했다. 이 과정에서 로봇 파일이 변경되면서 카메라 시야각이 틀어지고, 그리퍼가 교체되면서 Articulation 트리 구조가 바뀌었다. 각 변경 사항이 서로에게 미치는 영향(카메라 마운트 위치 → 색상 인식 좌표 → grasp 위치)이 사전에 공유되지 않으면 통합 단계에서 연쇄적인 디버깅 비용이 발생한다.

앞으로는 로봇 구성 변경 시 영향 범위(카메라, Articulation 경로, 조인트 파라미터)를 커밋 메시지에 명시하는 컨벤션이 필요하다.
