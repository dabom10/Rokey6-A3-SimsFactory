## 1. 오늘의 핵심 결정 — 스케일 롤백 및 로봇 교체

하루 전체를 관통하는 두 가지 거대한 결정이 모든 작업의 배경이 되었다. 이 결정들을 이해해야 이후 모든 작업의 맥락이 잡힌다.

### 1-1. 로봇 스케일 롤백 결정

**배경 및 문제 인식**

프로젝트 초기부터 우리는 로봇이 책장 선반 높이까지 닿지 않는 문제를 안고 있었다. 당시 선택한 임시방편은 로봇 에셋의 Scale 값을 2.68배로 키우는 것이었다. 이후 UR10에서 KR210으로 로봇 모델을 교체했을 때도 동일한 스케일 확대 방식을 그대로 유지했다.

그런데 이 방식에는 치명적인 구조적 결함이 있었다.

Isaac Sim(USD + PhysX)에서 객체의 Scale을 키우면 눈에 보이는 Mesh(형상)는 커지지만, 물리 엔진이 참조하는 속성들은 자동으로 보정되지 않는다. 구체적으로는 다음과 같은 문제가 발생한다.

- **질량(Mass):** 스케일이 커져도 MassAPI에 직접 입력된 수치는 그대로이므로, 외형은 거대한데 질량은 원본과 같은 비현실적인 상태가 된다.
- **관절 토크(Joint Torque):** DriveAPI의 Stiffness/Damping 수치도 원본 기준으로 설정되어 있어, 스케일이 커진 팔의 무게를 감당하지 못하거나 반대로 과도하게 작동한다.
- **충돌체(Collision Shape):** Convex Hull 기반의 충돌 형상이 스케일에 비례해 부정확하게 팽창하면서 실제 물체와 충돌 판정이 어긋나기 시작한다.
- **관성 텐서(Inertia Tensor):** 비례 스케일링 시 관성 텐서가 올바르게 재계산되지 않아 팔이 움직일 때 차체가 예측 불가능하게 흔들리거나 뒤집히는 현상이 생긴다.

이 모든 현상이 실제로 발생하고 있었고, 디버깅 시간을 갉아먹고 있었다.

> **최종 결정: UR10을 원본 스케일(1:1)로 복원하고, 월드(Environment) 전체를 로봇 크기에 맞춰 함께 축소한다.**

이 결정은 "로봇을 크게 키우는 것"을 포기하고 "세계를 로봇 크기에 맞게 줄이는 것"으로 방향을 전환한 것이다. 물리 정확도를 확보하기 위한 불가피한 선택이었고, kyb가 오전 새벽부터 환경 전체를 재구성하는 고된 작업을 감당해주었다.

## 3. 아키텍처 레벨의 핵심 의사결정

### 3-1. Perception 구조 재정의 — 오버엔지니어링 탈피

**초기 설계 (포기한 방향)**

처음에는 현실의 로봇 시스템을 최대한 모사하는 방향으로 Perception을 설계했다.

1. RGB 카메라 + Depth Camera를 로봇에 장착
2. Depth 이미지로 Point Cloud 생성
3. OpenCV로 특정 색상(빨간색) 큐브를 픽셀 단위로 추출
4. 픽셀 좌표 → 카메라 좌표계 → 월드 좌표계 변환 행렬을 적용해 큐브의 3D 위치 추정
5. 추정된 3D 좌표를 Grasping 목표점으로 전달

**문제 인식**

이 파이프라인은 실제 하드웨어에서는 당연히 필요하다. 그러나 시뮬레이터에서 이를 그대로 구현하는 것은 시뮬레이터의 핵심 이점을 스스로 포기하는 행위다. Isaac Sim의 USD Stage는 씬 내 모든 객체의 완벽한 절대 좌표(Ground-Truth)를 이미 알고 있다. 굳이 부정확할 수밖에 없는 카메라 기반 추정 과정을 거칠 이유가 없다.

더불어 Point Cloud 처리와 좌표계 변환은 디버깅 난이도가 매우 높고, 카메라 캘리브레이션 오차, 조명 조건 변화, 큐브 자세 변화 등 컨트롤하기 어려운 변수가 너무 많다. 이것을 구현하는 데 시간을 쏟다가는 정작 중요한 조작(Manipulation) 제어 품질이 떨어진다.

**최종 아키텍처**

| 역할 | 이전 설계 | 최종 설계 |
|---|---|---|
| 큐브 색상 판별 | OpenCV 색상 분류 | 카메라 단순 색상 분류(Classification)만 수행 |
| 큐브 위치 추적 | Depth Camera + 좌표 변환 | `cube_prim.GetWorldPose()` API 직접 호출 |
| 3D 좌표 획득 | Point Cloud 추정 | Stage에서 Ground-Truth 직접 읽기 |

카메라는 "이게 빨간 책인가 아닌가"를 판단하는 분류기 역할로만 남기고, 위치 정보는 API로 직접 가져오는 구조다. Perception 복잡도를 극단적으로 낮추는 대신, 팔이 실제로 물건을 잡는 Manipulation 제어 품질을 높이는 데 리소스를 집중할 수 있었다.

### 3-2. Navigation 전략 — "통합" 자체가 스펙

**고민했던 지점**

강화학습(RL) 기반 자율주행 네비게이션을 쓰지 않고 단순히 Waypoint(좌표)를 찍어 이동하는 방식을 택한 것이 기술적으로 너무 얕아 보이지 않을까 우려했다. "그냥 좌표로 이동하면 RL도 아니고 뭔가 빈약한 느낌 아닌가?"라는 내부 논의가 있었다.

**결론 및 근거**

프로젝트의 가치를 다시 정의했다. 본 프로젝트의 핵심 기술적 기여는 단일 AI 알고리즘의 성능이 아니다. **"모바일 베이스(주행) + 매니퓰레이터(조작) + 상태 기계(FSM)"라는 이질적인 세 요소를 하나의 파이프라인으로 엮어, Perception → Navigation → Manipulation이 끊김 없이 흐르는 End-to-End Task를 완성한 것** 자체가 시스템 엔지니어링 관점에서 의미 있는 성과다.

RL 네비게이션은 학습 시간과 환경 세팅에 상당한 비용이 들고, 그것이 잘 작동하지 않으면 파이프라인 전체가 블로킹된다. Waypoint 기반 이동으로 Navigation을 안정화한 뒤, 파이프라인 통합의 완성도를 높이는 것이 현 단계의 올바른 우선순위다.

## 4. 트러블슈팅

### 🚩 ISSUE 1 — Articulation Root 중복 및 컨트롤러 타겟 유실

**에러 로그**
```
[Error] Failed to find articulation at /Root/run_robot/body
[Error] Pattern did not match any rigid bodies: /Root/ur10_01
```

**현상**

모바일 베이스(`run_robot`)와 UR10 로봇 팔(`ur10_01`)을 USD 파일 내에서 하나의 씬으로 합치는 순간, Action Graph에 연결되어 있던 Articulation Controller가 완전히 먹통이 됐다. Play를 눌러도 로봇이 전혀 반응하지 않았고, 위 에러 로그가 콘솔을 가득 채웠다.

**원인 분석**

PhysX(Isaac Sim의 물리 엔진)는 조인트로 연결된 링크 체인 전체를 하나의 단일 동역학 트리(Articulation Tree)로 파악하고 계산한다. 이 트리에는 반드시 **단 하나의 루트(Root)** 가 존재해야 한다. 루트는 트리의 기준점이자 물리 계산의 시작점이기 때문이다.

그런데 우리는 모바일 베이스를 만들 때 차체(`run_robot/body`)에 `ArticulationRootAPI`를 붙였고, UR10을 세팅할 때도 별도로 UR10 프림(`ur10_01`)에 `ArticulationRootAPI`를 붙여놓은 상태였다. 두 객체를 합치자 하나의 Articulation Tree에 Root가 두 개가 생겨버린 것이다. PhysX 입장에서는 "이 트리의 머리가 어디냐"를 알 수 없으므로, 해당 Articulation 전체에 대한 물리 연산을 포기해버렸다.

```
[합치기 전]                         [합친 후 - 문제 상황]
run_robot/body  (Root ✅)           /Root/krobot
    └── wheels                          ├── run_robot/body  (Root ❌ 중복!)
                                        │       └── wheels
ur10_01  (Root ✅)                      └── ur10_01  (Root ❌ 중복!)
    └── joints/...                              └── joints/...
```

**해결 과정**

1. UR10 프림(`ur10_01`)에 붙어 있던 `ArticulationRootAPI`를 Properties 패널에서 제거했다.
2. 모바일 베이스와 UR10을 모두 포괄하는 최상위 Xform 프림(`/Root/krobot`)을 새로 만들고, 여기에만 `ArticulationRootAPI`를 단 1개 부여했다.
3. Action Graph 내 `Articulation Controller` 노드의 설정을 두 군데 모두 갱신했다.
   - `targetPrim` (관계 연결, Relationship): `/Root/krobot` 으로 재연결
   - `robotPath` (텍스트 속성, String): `/Root/krobot` 으로 재입력
   - ⚠️ 이 둘 중 하나만 바꾸면 여전히 동작하지 않는다. 반드시 두 개 모두 업데이트해야 한다.

```
[해결 후 - 올바른 구조]
/Root/krobot  (Root ✅ 단 1개)
    ├── run_robot/body
    │       └── wheels
    └── ur10_01
            └── joints/...
```

**핵심 교훈**

Isaac Sim에서 여러 USD 파일(혹은 에셋)을 합칠 때는, 각 에셋이 독립적으로 가지고 있던 `ArticulationRootAPI`가 충돌하지 않는지 반드시 확인해야 한다. 합친 후에는 전체 트리를 아우르는 최상위 노드 하나에만 Root를 부여하는 것이 원칙이다.

### 🚩 ISSUE 2 — 관절 위치 제어 불능 (DriveAPI 타이밍 문제) ★ 핵심 발견

**현상**

Action Graph에서 target 각도 값을 바꾸어도 로봇 팔이 전혀 움직이지 않거나, 목표 각도에 거의 다다를 듯 하다가 0.816rad 오차 지점에서 멈추고 그 이상 나아가지 않는 현상이 반복됐다. 콘솔 에러는 없었기에 더욱 찾기 어려웠다.

**원인 ① — 조인트 경로 하드코딩**

기존 코드는 로봇의 조인트를 찾을 때 다음과 같이 경로를 고정해 놓고 있었다.

```python
# 잘못된 방식 - KR210의 실제 구조와 맞지 않음
joint_path = f"{robot_path}/joints/{joint_name}"
drive = UsdPhysics.DriveAPI.Apply(stage.GetPrimAtPath(joint_path), "angular")
drive.GetStiffnessAttr().Set(1e7)
```

UR10은 `joints/` 폴더 아래에 조인트가 모여 있는 구조지만, KR210은 각 `link_N` 내부에 개별 조인트가 분산되어 있는 구조다. 즉, `joints/shoulder_pan_joint` 같은 경로로 탐색하면 KR210의 조인트는 아예 찾지 못하고, Stiffness 설정 자체가 실패로 끝나버렸다.

**원인 ② — PhysX 초기화 타이밍 (치명적)**

이것이 진짜 핵심 원인이었다. 우리 코드의 구조는 대략 다음과 같았다.

```python
async def setup_scene(self):
    # 씬 로드, 로봇 추가 등...
    pass

async def on_physics_step(self, step_size):
    await world.play_async()  # ← Play 시작
    # ... Play 이후에 DriveAPI 설정
    drive.GetStiffnessAttr().Set(1e7)   # ← 이게 문제!
    drive.GetDampingAttr().Set(1e5)
```

PhysX 엔진의 동작 방식은 이렇다. **Play 버튼이 눌리는 순간, 엔진은 그 시점의 USD Stage 전체를 스냅샷으로 읽어 물리 환경을 초기화(Bake)한다.** 이후 런타임 중에 파이썬 코드로 아무리 `DriveAPI` 속성을 변경해도, 그것은 USD Stage의 속성 패널 숫자만 바꿀 뿐이다. 이미 초기화를 마친 PhysX 내부 상태에는 전혀 반영되지 않는다.

다시 말해, Stiffness가 0(또는 초기값)인 채로 PhysX가 초기화되었기 때문에 아무리 target을 바꿔도 관절이 움직일 힘(토크)이 없었던 것이다.

**해결**

```python
# ✅ 올바른 방식

async def setup_scene(self):
    # --- 반드시 Play 이전(Stop 상태)에 수행 ---

    # 1) 하드코딩 폐기: Usd.PrimRange로 트리 전체를 순회하며 조인트 동적 탐색
    for prim in Usd.PrimRange(robot_prim):
        if prim.GetTypeName() == "PhysicsRevoluteJoint":
            drive = UsdPhysics.DriveAPI.Apply(prim, "angular")
            drive.GetStiffnessAttr().Set(1e7)   # ← Play 이전에 설정 완료
            drive.GetDampingAttr().Set(1e5)

    # 2) MassAPI도 동일하게 Play 이전에 설정
    mass_api = UsdPhysics.MassAPI.Apply(body_prim)
    mass_api.GetMassAttr().Set(20.0)

# Play 이후에는 DriveAPI를 건드리지 않는다
async def on_physics_step(self, step_size):
    # 제어 로직만 수행
    ...
```

`Usd.PrimRange`를 사용하면 트리를 재귀적으로 순회하므로, 조인트가 어느 깊이에 있든, 어떤 구조로 분산되어 있든 모두 찾아낼 수 있다. 그리고 모든 물리 속성 설정은 `setup_scene()` 안에서, 즉 **Play 이전의 Stop 상태**에서 완료해야 한다.

**핵심 교훈**

Isaac Sim에서 물리 속성(DriveAPI, MassAPI, CollisionAPI 등)을 설정하는 코드는 **반드시 `world.play_async()` 이전 단계에서 실행**되어야 한다. Play 이후에 속성을 변경하고 싶다면 `world.stop()` → 속성 변경 → `world.play_async()` 사이클을 거쳐야 한다.

### 🚩 ISSUE 3 — 차체 굴러감 및 흔들림 (단일 트랜잭션의 원칙)

**현상**

로봇 팔이 목표 위치를 향해 뻗는 순간, 차체가 뒤로 밀리거나 앞뒤로 덜덜 떨렸다. 심한 경우 차체 자체가 굴러다니며 시뮬레이션이 발산했다. 팔이 멈추면 차체도 어느 정도 안정되지만, 팔이 움직이는 동안에는 제어 불능 상태였다.

**원인 ① — 바퀴 드라이브의 복원 토크**

바퀴 조인트에 `Position Drive`(위치 제어)가 설정되어 있었다. Position Drive는 조인트를 특정 각도 위치에 유지하려는 힘을 지속적으로 발생시킨다. 팔이 움직여 차체에 반력이 전달되는 순간, 바퀴 조인트의 Position Drive가 "아, 지금 위치에서 밀렸으니 원래대로 돌아가야 해"라는 복원 토크를 발생시키면서 차체가 진동하기 시작했다.

**원인 ② — Isaac Sim API의 단일 트랜잭션 원칙 위반**

이것이 더 근본적인 원인이었다. 당시 코드는 팔과 바퀴를 따로 제어하고 있었다.

```python
# ❌ 잘못된 방식 - 한 프레임에 동일 Articulation에 두 번 명령
articulation.apply_action(arm_action)          # 팔 제어
articulation.set_joint_velocities(wheel_vels)  # 바퀴 제어
```

Isaac Sim Core API의 동작 규칙이 있다. **동일한 Articulation 객체에 대해 한 물리 프레임(Physics Step) 내에 여러 명령이 들어오면, 가장 마지막 명령만 적용되고 이전 명령들은 모두 무시된다.**

즉, `apply_action`으로 팔 제어 명령을 보냈지만, 바로 이어진 `set_joint_velocities`가 그것을 덮어써버렸다. 결과적으로 팔 제어 명령은 매 프레임 소거되었고, 바퀴 명령도 안정적으로 적용되지 않아 브레이크가 풀린 것처럼 차체가 표류했다.

**해결**

```python
# ✅ 올바른 방식 - 한 프레임에 단 1회의 apply_action으로 전체 제어

# 1) 바퀴의 영구 Position Drive 설정 제거 (setup_scene에서)
#    → 바퀴에는 아무 Drive도 걸지 않음

# 2) 런타임에 바퀴 조인트에 포지션 락 부여
#    (현재 위치를 그대로 유지하도록 Stiffness를 높게 설정)
articulation.set_joint_stiffnesses(wheel_indices, [1e6] * num_wheels)
current_wheel_positions = articulation.get_joint_positions(wheel_indices)

# 3) 팔 목표 각도 계산 (Lerp 스무딩 적용)
current_arm_pos = articulation.get_joint_positions(arm_indices)
target_arm_pos = lerp(current_arm_pos, goal_arm_pos, alpha=0.05)

# 4) 팔 명령 + 바퀴 락 포지션을 단일 배열로 병합
full_action = np.concatenate([target_arm_pos, current_wheel_positions])
full_indices = np.concatenate([arm_indices, wheel_indices])

# 5) 단 1회 apply_action으로 전송
articulation.apply_action(ArticulationAction(
    joint_positions=full_action,
    joint_indices=full_indices
))
```

모든 조인트(팔 + 바퀴)에 대한 명령을 `np.concatenate`로 하나의 배열로 합친 뒤, 매 물리 프레임마다 **딱 한 번만 `apply_action`을 호출**하는 구조로 바꿨다. 바퀴는 "현재 위치 그대로 유지"라는 명령을 받으므로 외력(팔의 반력)에도 흔들리지 않게 된다.

**핵심 교훈**

Isaac Sim에서 하나의 Articulation을 제어할 때는 **한 물리 스텝(프레임) 당 `apply_action` 또는 제어 함수 호출이 정확히 1회여야 한다.** 팔, 바퀴, 그리퍼 등 여러 부위를 동시에 제어해야 한다면, 각각의 명령을 별도로 호출하지 말고 단일 배열로 병합하여 한 번에 보내는 것이 규칙이다.

### 🚩 ISSUE 4 — 흡착형 그리퍼 (Surface Gripper) 구현

**현상**

물리 기반의 Parallel Gripper(두 핑거가 오므라들며 잡는 방식)를 구현했으나, 큐브를 집을 때 자꾸 미끄러지거나 떨어뜨렸다. 특히 큐브를 집어 올린 후 이동하는 과정에서 불안정한 물리 충돌로 인해 큐브가 튀거나 뒤집히는 현상이 빈번하게 발생했다.

**문제의 본질**

물리 기반 그리핑의 안정성은 마찰 계수, 접촉 면적, 접촉 힘 등 여러 물리 파라미터의 미세한 균형에 크게 의존한다. 시뮬레이터에서 이것을 현실과 완전히 동일하게 재현하는 것은 매우 어렵고, 파라미터 튜닝에 상당한 시간이 소요된다.

**해결 — SetParent 기반 강제 흡착 방식 채택**

물리 엔진의 계산 결과에 의존하는 대신, 큐브와 그리퍼가 충분히 가까워지는 순간 USD의 Prim 계층 구조를 직접 변경하는 방식을 채택했다.

```python
def attach_cube(self, cube_prim, gripper_prim):
    """큐브를 그리퍼의 자식 노드로 편입시켜 강제 흡착"""
    # 큐브의 현재 월드 좌표 저장
    world_pos, world_rot = cube_prim.GetWorldPose()

    # 큐브를 그리퍼의 자식으로 재부모화
    cube_prim.prim.SetParent(gripper_prim.prim)

    # 로컬 좌표 재계산하여 위치 유지
    local_pos = compute_local_pose(gripper_prim, world_pos, world_rot)
    cube_prim.set_local_pose(local_pos)

def detach_cube(self, cube_prim, world_prim):
    """큐브를 월드로 분리하여 놓기"""
    world_pos, world_rot = cube_prim.GetWorldPose()
    cube_prim.prim.SetParent(world_prim)
    cube_prim.set_world_pose(world_pos, world_rot)
```

`SetParent(gripper_prim)`를 호출하면 큐브가 로봇 팔의 자식 노드가 되므로, 이후 팔이 움직이면 큐브도 팔의 좌표계를 따라 완벽하게 함께 이동한다. 물리적 마찰 계산 없이 100% 안정적으로 큐브를 운반할 수 있다.

**핵심 교훈**

시뮬레이터에서 그리핑 안정성보다 Pick & Place 태스크 파이프라인 전체의 안정성이 더 중요한 경우, 물리 기반 그리핑을 USD 계층 구조 변경 방식으로 대체하는 것이 유효한 선택이다. 물론 이 방법은 현실의 그리퍼를 정확히 모사하지 않으므로, 현실 적용이 목표라면 별도의 물리 기반 그리핑 연구가 필요하다.

### 🚩 ISSUE 5 — 라이다 시야각 가림 (해결 중 🔧)

**현상**

라이다(Lidar) 센서의 FOV(Field of View)를 360도로 설정했음에도 불구하고, 실제 스캔 결과가 전방 일부 영역만 부채꼴(피자 조각) 모양으로 찍혔다. 나머지 방향은 스캔 데이터가 아예 없거나 극히 짧은 거리에서 차단되어 있었다.

**원인 분석**

신규 차체 설계 구조에서 비롯된 문제다.

기존의 통짜 박스 차체를 위아래 두 개의 큐브로 분리하고, 그 사이 공간에 라이다 센서를 삽입하는 구조로 변경했다. 이 공간은 앞쪽으로는 열려 있지만, 나머지 방향은 차체 구조물(큐브 기둥, 연결 프레임)과 위에 장착된 UR10 베이스가 막고 있는 형태다.

Isaac Sim의 라이다는 레이캐스트(Raycast) 방식으로 작동한다. 센서에서 사방으로 레이저를 쏘고, 첫 번째로 충돌하는 면까지의 거리를 기록한다. 후방 및 측방으로 쏘는 레이저가 차체 구조물에 즉각 충돌하므로, 그 방향의 스캔 데이터는 모두 "매우 가까운 차체 표면"으로 기록되거나, 필터링 임계값 이하로 처리되어 유효 데이터에서 제외된다.

```
[라이다 시야 가림 구조도]

       수납박스
    ┌──────────┐
    │          │   ← UR10 베이스가 후방 레이저 차단
    │  라이다   │
    │    (*)   │
    └──────────┘
    [큐브 하단]       ← 차체 기둥이 측방/후방 레이저 차단
       바퀴들

  → 앞쪽만 열려있어 전방 부채꼴만 스캔됨
```

시뮬레이터가 레이캐스트 충돌을 현실적으로 계산한 결과이며, 차체를 X-Ray처럼 통과하지 않는 이상 구조적으로 피할 수 없는 문제였다.

**시도한 해결 방법 및 결과**

| 시도 | 방법 | 결과 |
|---|---|---|
| 1차 | 라이다 Z축을 높여 차체 상단 위로 올림 | 여전히 피자 조각 모양으로 스캔됨. UR10 베이스가 여전히 후방을 막음 |

단순 위치 조정으로는 해결이 불가하다는 것을 확인했다. 차체 구조물 자체가 라이다의 물리적 시야를 막고 있는 것이므로, 위치를 바꾸는 것만으로는 한계가 있다.

**현재 상태 및 다음 시도 방향**

1. **RTX Lidar로 교체:** Isaac Sim의 RTX 기반 라이다는 일반 Raycast Lidar와 다르게 센서 파라미터 및 필터링 동작이 다를 수 있다. 교체 후 동작 차이를 확인할 필요가 있다.
2. **차체 구조 재검토:** 라이다를 차체 사이가 아닌 상단 돌출 마운트에 올리거나, 라이다 주변 구조물의 Collision을 비활성화하는 방식을 검토 중이다.

### 🚩 ISSUE 6 — Isaac Sim 강제 종료 (코어 덤프, Asset Root 구조 오염)

**에러 로그**
```
Segmentation fault (core dumped)
```

**현상**

프로젝트를 진행하던 중 어느 시점부터 Isaac Sim이 시뮬레이션 실행 도중 갑자기 강제 종료되기 시작했다. 에러 메시지는 `코어 덤프됨` 계열의 치명적 오류였고, 재현도 불규칙하게 발생하여 원인을 특정하기가 어려웠다.

**원인 분석 — Asset 내부에 직접 객체 추가**

우리가 구성한 씬의 구조를 다시 살펴보면 다음과 같았다.

1. Isaac Sim의 Asset Browser에서 Environment 에셋(`.usd` 파일)을 불러왔다.
2. 불러온 에셋의 Stage 내부 Root(예: `/Root`) 아래에 **직접** 로봇, 컨베이어, 큐브 등을 추가했다.

이것이 문제였다. Isaac Sim에서 외부 에셋을 씬에 불러오면 해당 에셋은 **Sublayer 또는 Reference** 형태로 현재 Stage에 연결된다. 이 에셋의 Root는 어디까지나 "외부 파일의 내용을 읽어오는 참조"이며, 그 아래에 새로운 프림을 직접 추가하면 USD의 레이어 합성(Composition Arc) 규칙이 깨지기 시작한다.

일반적으로 Isaac Sim의 씬 작업은 **`World`라는 이름의 최상위 Xform 아래에서 모든 것을 구성**하는 것이 권장 방식이다. 에셋은 Reference로 불러와 `World` 아래 적당한 위치에 배치하되, 에셋 내부 구조를 직접 수정하거나 그 안에 새 객체를 추가하는 것은 피하는 것이 원칙이다.

참고로 에셋 내부 요소를 **삭제**하는 것은 USD의 Override 레이어로 처리가 가능해 비교적 안전하다. 그러나 **추가**하는 것은 레이어 합성 규칙을 위반하게 되어 PhysX 초기화 시 충돌이 발생하고, 이것이 세그멘테이션 폴트(코어 덤프)로 이어진 것으로 파악된다.

```
[권장 Stage 구조]                   [우리의 문제 구조]
/World  ← Isaac Sim 표준 루트       /Root  ← 에셋의 루트
  ├── Environment (Reference)           ├── environment_mesh
  │     └── [에셋 내용, 건드리지 않음]   ├── robot    ← 직접 추가 ❌
  ├── robot                             └── conveyor ← 직접 추가 ❌
  └── conveyor
```

**해결 — Save Flatten As로 Stage 구조 정리**

Isaac Sim에서 이 문제를 해결하는 가장 확실한 방법은 **`File → Save Flatten As...`** 기능을 사용하는 것이다.

`Save Flatten As`는 현재 Stage에 Reference, Sublayer, Payload 등 여러 레이어로 복잡하게 얽혀 있는 USD Composition을 모두 펼쳐서(Flatten) 단일 USD 파일로 통합해준다. 이렇게 생성된 파일은 외부 참조 없이 자기 완결적인 구조를 가지므로, 레이어 구조 오염 문제가 근본적으로 해소된다.

**권장 작업 절차 (앞으로 이렇게 하자)**

1. 새 Stage를 열면 최상위에 `World`라는 이름의 Xform을 먼저 생성한다.
2. 사용할 Environment 에셋을 Reference로 불러와 `World` 아래에 배치한다.
3. 로봇, 컨베이어, 큐브 등 추가 객체는 모두 `World` 아래 별도 Xform 노드로 추가한다. 에셋 내부 경로에는 절대 추가하지 않는다.
4. 여러 객체의 위치·그룹 관리가 필요하다면 Stage에서 Xform을 폴더처럼 활용해 계층을 정리한다.
5. 씬 구성이 어느 정도 완료되면 `File → Save Flatten As...`로 저장하여 레이어 구조를 깔끔하게 통합한다.

**핵심 교훈**

Isaac Sim에서 불러온 에셋(Asset)은 내용을 참조하는 용도로만 써야 한다. 에셋 내부 요소의 삭제는 가능하지만, **새로운 객체를 추가하는 것은 Stage 구조를 오염시키고 코어 덤프로 이어질 수 있다.** 에셋 위에서 작업을 많이 했다면 `Save Flatten As`로 Stage를 주기적으로 정리하는 습관을 들이자.

### 🚩 ISSUE 7 — DynamicCuboid 네이밍 충돌

**에러 로그**
```
cannot add the object cube to the scene since its name is not unique
```

**현상**

Play → Stop → Play를 반복할 때, 즉 시뮬레이션을 재시작할 때마다 위 에러가 발생하며 씬에 큐브가 추가되지 않았다.

**원인**

`world.scene.add(DynamicCuboid(name="cube", ...))`를 매 실행마다 호출하는데, 이전 Play에서 씬에 추가된 `cube` 객체가 Stop 후에도 완전히 제거되지 않고 씬 레지스트리에 남아 있었기 때문이다. 두 번째 Play 시 동일한 이름(`cube`)으로 다시 추가하려 하자 이름 중복 에러가 발생했다.

**해결**

씬에 객체를 추가하기 전, 해당 이름의 프림이 이미 존재하는지 확인하고 존재하면 먼저 제거하는 방어 로직을 추가했다.

```python
async def setup_scene(self):
    # 씬 초기화 방어 로직
    if world.scene.object_exists("cube"):
        world.scene.remove_object("cube")

    # 이후 정상 추가
    world.scene.add(DynamicCuboid(
        prim_path="/World/cube",
        name="cube",
        position=np.array([0.5, 0.0, 0.05]),
    ))
```

**핵심 교훈**

Python Extension 방식으로 Isaac Sim을 반복 실행할 때는 씬 객체가 이전 실행에서 완전히 정리되지 않는 경우가 있다. 씬에 객체를 추가하는 코드 앞에 항상 존재 여부 확인 + 제거 로직을 넣는 것이 안전하다.

### 🚩 ISSUE 8 — Git Divergent Branch (협업 충돌)

**현상**

`git pull` 시도 시 다음과 같은 에러가 발생했다.

```
hint: You have divergent branches and need to specify how to reconcile them.
fatal: Need to specify how to reconcile divergent branches.
```

로컬과 원격 저장소의 커밋 히스토리가 갈라진(diverge) 상태가 되어 단순 pull이 불가한 상황.

**원인**

여러 팀원이 동시에 같은 브랜치에 커밋하면서 서로 다른 히스토리 라인이 생성됐다.

**해결**

Merge 커밋(히스토리에 불필요한 분기점)을 남기지 않기 위해 Rebase 전략을 채택했다.

```bash
git config pull.rebase true    # 이 저장소의 기본 pull 전략을 rebase로 설정
git pull                        # rebase 방식으로 충돌 해소
```

Rebase는 로컬 커밋들을 원격의 최신 커밋 위에 재배치하므로, 히스토리가 선형으로 유지되어 협업 이력을 추적하기 훨씬 용이하다.

## 5. 회고 — Lessons Learned

**Isaac Sim은 USD Hierarchy 이해가 50%다.**
Stage 탭에 렌더링된 트리 구조가 법이다. 경로가 하나라도 틀리면 아무리 훌륭한 파이썬 로직도 허공에 삽질이다. 특히 여러 에셋을 합칠 때 Root 구조가 충돌하지 않는지, 경로 참조가 올바른지 항상 Stage 탭으로 먼저 확인하자.

**물리 엔진(PhysX)은 거짓말을 하지 않는다.**
제어 신호가 완벽해도 Stiffness가 0이거나 질량이 종잇장이라면 로봇은 날아간다. 그리고 DriveAPI 설정 코드가 Play 이후에 있다면, 아무리 올바른 값을 써도 PhysX는 그것을 모른다. 소프트웨어 로직을 디버깅하기 전에 **Drive/Mass/Inertia 등 하드웨어 물리 속성이 Play 이전에 올바르게 설정되었는지를 먼저 점검하는 Physics-First 사고방식**이 핵심이다.

**복잡함이 항상 정답은 아니다.**
Depth Camera 기반 Point Cloud와 RL 주행을 과감히 포기하고 Ground-Truth 좌표와 FSM 제어로 선회한 결정이 신의 한 수였다. 덕분에 로봇 팔 + 모바일 베이스 + Pick & Place 시퀀스를 완벽히 하나로 통합하는, 진짜 의미 있는 시스템 엔지니어링 역량을 보여줄 수 있었다.

**에셋(Asset)은 참조 용도로만 사용하라.**
Isaac Sim에서 불러온 에셋의 내부 구조를 직접 수정하거나 그 안에 객체를 추가하는 것은 Stage 레이어 구조를 오염시켜 코어 덤프로 이어질 수 있다. 항상 별도의 `World` 노드 아래에서 작업하고, 작업이 복잡해졌다면 `Save Flatten As`로 정기적으로 Stage를 정리하자.
